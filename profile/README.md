## :triangular_flag_on_post: Now

현재 1학년 3명과 3학년 2명이 함께  
첫 번째 공모전 프로젝트의 주제와 구현 범위를 검토하고 있습니다.

주요 준비 사항은 다음과 같습니다.

- 제13회 전국 ICT융합 AI 공모전 참가 조건과 제출 범위 확인
- 기존 아이디어와 신규 아이디어 비교
- 소프트웨어·AI·하드웨어 융합 가능성 검토
- 팀원별 기술 경험, 관심 분야와 투입 가능 시간 확인
- 5명이 기능 단위로 협업할 수 있는 최소 기능 선정
- 김창수 교수님께 지도교수 및 기술 자문 요청 준비
- 프로젝트에 필요한 장비·부품과 자재 확보 경로 확인
- GitHub 기반 역할·Issue·Pull Request 운영 방식 정리

**하드웨어는 아이디어에 필요하다는 이유만으로 먼저 포함하지 않습니다.**

**장비 보유 여부, 자재비, 제작 기간과 통합 난도를 확인**한 뒤  
**마감일까지 안정적으로 완성할 수 있을 때만 적용**합니다.

첫 프로젝트는 기술의 수나 외형의 화려함보다  
**팀이 직접 구현하고 테스트하며 설명할 수 있는 범위**를 기준으로 선택합니다.

## :book: About

**PaiChai Dev 26**은 공모전과 팀 프로젝트를 통해  
아이디어가 실제 결과물로 만들어지는 전체 과정을 경험하기 위해 시작한 학생팀입니다.

현재 배재대학교 컴퓨터공학전공  
**1학년 3명과 3학년 2명**, 총 5명이 함께하고 있습니다.

한 번의 대회나 수상만을 위한 팀이 아닙니다.

문제를 조사하고 구현 가능한 범위로 줄인 뒤,  
기능·역할·일정과 완료 기준을 정하고  
직접 설계·개발·테스트·발표하는 과정을 반복합니다.

프로젝트가 끝난 뒤에는 코드와 발표 자료뿐 아니라  
의사결정, 시행착오, 실패 원인과 회고까지 정리합니다.

구성원마다 학년과 프로젝트 경험은 다르지만,  
일부 구성원이 프로젝트 전체를 대신 수행하지 않습니다.

서로의 경험을 활용하면서도 모든 팀원이  
자신의 코드, 테스트, 데이터, 하드웨어, 문서 또는 발표 산출물을 직접 책임합니다.

> PaiChai Dev 26은 학생들이 자율적으로 운영하는 프로젝트팀입니다.  
> 현재 특정 교수님, 연구실 또는 학교 기관의 공식 조직을 의미하지 않습니다.  
> 지도교수와 기관의 참여는 정식 승낙 이후에만 표기합니다.

## Why We Build

우리가 프로젝트를 수행하는 목적은  
결과물 하나를 제출하는 데 그치지 않습니다.

- 막연한 아이디어를 검증 가능한 문제로 줄이는 경험
- 공모전 규정과 평가 기준을 실제 개발 범위에 반영하는 경험
- 학년과 경험이 다른 구성원이 협업하는 경험
- 팀원의 기술 수준과 일정에 맞게 작업을 나누는 경험
- 서로 다른 코드와 문서를 하나의 결과물로 통합하는 경험
- 소프트웨어와 하드웨어의 필요성을 구분하는 경험
- 오류와 실패 원인을 찾아 수정하는 경험
- 기술 내용을 문서와 발표로 설명하는 경험
- 프로젝트 종료 후 다음 활동에 적용할 회고를 남기는 경험

프로젝트마다 완벽한 결과보다  
**끝까지 한 사이클을 완주하고 다음 프로젝트에서 더 나아지는 것**을 중요하게 생각합니다.

## Project Cycle

```text
Explore → Define → Validate → Plan → Build → Test → Present → Review
```

| Stage | 주요 활동 | 남기는 기록 |
|---|---|---|
| **Explore** | 공모전, 문제, 사용자와 관련 기술 조사 | 후보 비교표, 참고 자료 |
| **Define** | 해결할 문제와 제외할 범위 결정 | 문제 정의, 프로젝트 범위 |
| **Validate** | 데이터·장비·기술·일정의 실현 가능성 확인 | 기술 검토, 자재 목록, 위험요소 |
| **Plan** | 기능·역할·일정·완료 기준 설정 | 일정표, Issue, 역할표 |
| **Build** | 기능과 문서를 작은 단위로 구현 | 코드, 회로, 문서, 작업 기록 |
| **Test** | 기능 통합과 오류·한계 확인 | 테스트 결과, 오류 기록 |
| **Present** | 시연과 발표 자료 완성 | 발표 자료, 시연 자료 |
| **Review** | 성과와 실패 원인 정리 | 회고, 다음 개선사항 |

모든 단계를 처음부터 완벽하게 수행하지는 못할 수 있습니다.

대신 부족했던 단계와 의사결정의 원인을 기록하고  
다음 프로젝트에서 같은 문제가 반복되지 않도록 개선합니다.

자세한 운영 흐름은  
[`docs/PROJECT_CYCLE.md`](../docs/PROJECT_CYCLE.md)에 정리합니다.

## How We Work

### 1. 문제를 먼저 정합니다

AI, IoT, 임베디드, 웹과 같은 기술을 먼저 고른 뒤  
기술을 사용할 문제를 억지로 찾지 않습니다.

누가 어떤 불편을 겪고 있는지,  
기존 방식의 한계가 무엇인지 먼저 확인합니다.

### 2. 작게 시작합니다

처음부터 큰 시스템을 만들기보다  
마감일까지 실제로 작동시킬 수 있는 최소 기능부터 정합니다.

핵심 흐름이 완성되기 전에는  
부가 기능이나 외형 확장에 시간을 사용하지 않습니다.

### 3. 역할보다 작업을 구체적으로 나눕니다

`AI 담당`, `백엔드 담당`, `하드웨어 담당` 같은 넓은 명칭보다  
완료 여부를 확인할 수 있는 작업 단위로 나눕니다.

```text
공개 데이터 1종 정리하기
입력값 검증 로직 구현하기
API 엔드포인트 1개 구현하기
결과 화면 1개 만들기
센서 데이터 수집 코드 작성하기
테스트 사례 10개 작성하기
부품 목록과 예상 자재비 정리하기
발표용 시스템 구조도 작성하기
```

### 4. 학년보다 담당 결과물로 책임을 구분합니다

선배가 모든 핵심 기능을 대신하거나  
저학년이 조사·문서·발표만 담당하는 구조를 지양합니다.

경험이 많은 구성원은 설계와 코드 리뷰를 지원할 수 있지만,  
각 구성원은 자신의 작업을 직접 구현하고 설명할 수 있어야 합니다.

### 5. 한 사람이 모든 일을 대신하지 않습니다

팀장은 범위, 일정과 결과물 통합을 관리하지만  
각 팀원은 자신의 작업과 산출물을 직접 책임합니다.

일정이 늦어졌다는 이유로 한 사람이 다른 사람의 작업을  
반복해서 대신 완성하는 방식으로 운영하지 않습니다.

### 6. Pull Request와 Review를 사용합니다

기능별 Issue와 브랜치를 만들고  
Pull Request를 통해 변경 내용과 테스트 결과를 공유합니다.

중요 기능과 구조 변경은  
최소 한 명 이상의 검토를 거쳐 반영하는 것을 원칙으로 합니다.

리뷰는 작성자를 평가하는 과정이 아니라  
오류와 통합 위험을 줄이는 과정으로 봅니다.

### 7. 하드웨어는 필요성과 비용을 검증합니다

하드웨어는 시연 효과만을 위해 추가하지 않습니다.

다음 항목을 확인한 뒤 포함 여부를 결정합니다.

- 문제 해결에 실제로 필요한가
- 학교·학과·연구실 장비를 사용할 수 있는가
- 부품과 자재비를 확보할 수 있는가
- 제작과 배송 기간이 일정에 맞는가
- 소프트웨어와 통합 테스트가 가능한가
- 고장 시 대체 시연 방법이 있는가

장비와 자재를 확보하지 못한 기능은  
확정 기능처럼 문서에 표시하지 않습니다.

### 8. 모르는 것을 숨기지 않습니다

처음 접하는 기술과 개념은 함께 공부합니다.

학습 자료, 막힌 문제, 실패한 시도와 해결 과정도  
프로젝트 기록의 일부로 봅니다.

### 9. AI 사용 범위를 기록합니다

AI 도구를 코드 작성, 문서 초안, 아이디어 정리에 사용할 수 있지만  
생성된 결과를 검토하지 않은 채 그대로 반영하지 않습니다.

각 구성원은 자신이 제출한 코드와 문서를 직접 설명할 수 있어야 하며,  
사용한 모델·도구와 검증 방법을 필요한 범위에서 기록합니다.

### 10. 결과를 과장하지 않습니다

실제로 작동한 범위와 테스트 조건을 명확히 적습니다.

사용하지 않은 기술, 확보하지 못한 장비,  
측정하지 않은 성능을 결과처럼 표시하지 않습니다.

### 11. 대회가 끝나도 정리합니다

제출 이후에도 실행 방법, 주요 기능, 테스트 결과,  
미완성 항목과 다음 프로젝트에서 개선할 점을 남깁니다.

세부 원칙은  
[`docs/TEAM_RULES.md`](../docs/TEAM_RULES.md)를 따릅니다.

## Projects

현재 첫 번째 프로젝트의 아이디어와 범위를 검토하고 있습니다.

주제가 확정되기 전에는 특정 아이디어를  
팀의 공식 프로젝트로 표시하지 않습니다.

프로젝트 선정 기준은 다음과 같습니다.

- 해결하려는 사용자와 문제가 명확한가
- 제13회 전국 ICT융합 AI 공모전의 취지에 부합하는가
- AI 또는 ICT 기술의 역할을 구체적으로 설명할 수 있는가
- 단순한 AI API 호출을 넘어 검증 가능한 기능이 있는가
- 5명이 기능 단위로 작업을 나눌 수 있는가

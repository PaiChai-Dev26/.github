## Now

현재 첫 번째 프로젝트를 선정하기 위해 다음 작업을 진행하고 있습니다.

- 참여 가능한 공모전과 참가 규정 비교
- 팀 수준에 맞는 문제와 최소 기능 검토

첫 프로젝트는 대회 이름이나 기술의 화려함보다  
**팀이 직접 완주하고 설명할 수 있는 범위**를 기준으로 선택합니다.

## About

**PaiChai Dev 26**은 공모전과 팀 프로젝트를 통해  
아이디어가 실제 결과물로 만들어지는 전체 과정을 경험하기 위해 시작한 학생팀입니다.

한 번의 대회나 수상만을 위한 팀이 아닙니다.

문제를 조사하고, 구현 가능한 범위로 줄이고,  
역할과 일정을 나눈 뒤 직접 개발·테스트·발표하는 과정을 반복합니다.

프로젝트가 끝난 뒤에는 코드와 발표 자료뿐 아니라  
의사결정, 시행착오, 실패 원인과 회고까지 정리합니다.

현재 구성원은 모두 컴퓨터공학전공 학생이며,  
완성된 전문가들이 모인 팀보다 여러 프로젝트를 함께 수행하며  
각자의 기술적 관심과 역할을 찾아가는 팀에 가깝습니다.

> PaiChai Dev 26은 학생들이 자율적으로 운영하는 프로젝트팀입니다.  
> 현재 특정 교수님, 연구실 또는 학교 기관의 공식 조직을 의미하지 않습니다.

## Why We Build

우리가 프로젝트를 수행하는 목적은 결과물 하나를 제출하는 데 그치지 않습니다.

- 막연한 아이디어를 실행 가능한 문제로 줄이는 경험
- 팀원의 수준과 일정에 맞게 작업을 나누는 경험
- 서로 다른 코드와 문서를 하나의 결과물로 통합하는 경험
- 오류와 실패 원인을 찾아 수정하는 경험
- 기술 내용을 문서와 발표로 설명하는 경험
- 프로젝트 종료 후 다음 활동에 적용할 회고를 남기는 경험

프로젝트마다 완벽한 결과보다  
**끝까지 한 사이클을 완주하고 다음 프로젝트에서 더 나아지는 것**을 중요하게 생각합니다.

## Project Cycle

```text
Explore → Define → Plan → Build → Test → Present → Review
```

| Stage | 주요 활동 | 남기는 기록 |
|---|---|---|
| **Explore** | 공모전, 문제, 사용자와 관련 기술 조사 | 후보 비교표, 참고 자료 |
| **Define** | 해결할 문제와 제외할 범위 결정 | 문제 정의, 프로젝트 범위 |
| **Plan** | 기능·역할·일정·완료 기준 설정 | 일정표, Issue, 역할표 |
| **Build** | 기능과 문서를 작은 단위로 구현 | 코드, 문서, 작업 기록 |
| **Test** | 기능 통합과 오류·한계 확인 | 테스트 결과, 오류 기록 |
| **Present** | 시연과 발표 자료 완성 | 발표 자료, 시연 자료 |
| **Review** | 성과와 실패 원인 정리 | 회고, 다음 개선사항 |

모든 단계를 처음부터 완벽하게 수행하지는 못할 수 있습니다.  
대신 부족했던 단계를 확인하고 다음 프로젝트에서 보완합니다.

자세한 운영 흐름은 [`docs/PROJECT_CYCLE.md`](../docs/PROJECT_CYCLE.md)에 정리합니다.

## How We Work

### 1. 작게 시작합니다

처음부터 큰 시스템을 만들기보다  
마감일까지 실제로 작동시킬 수 있는 최소 기능부터 정합니다.

### 2. 역할보다 작업을 구체적으로 나눕니다

`AI 담당`, `백엔드 담당` 같은 넓은 명칭보다  
다음처럼 확인 가능한 작업 단위로 나눕니다.

```text
공개 데이터 1종 정리하기
입력값 검증 로직 구현하기
결과 화면 1개 만들기
테스트 사례 5개 작성하기
발표용 구조도 작성하기
```

### 3. 모르는 것을 숨기지 않습니다

처음 접하는 기술과 개념은 함께 공부합니다.  
학습 자료, 막힌 문제와 해결 과정도 프로젝트 기록의 일부로 봅니다.

### 4. 한 사람이 모든 일을 대신하지 않습니다

팀장은 범위, 일정과 결과물 통합을 관리하지만  
각 팀원은 자신의 작업과 산출물을 직접 책임집니다.

### 5. 결과를 과장하지 않습니다

실제로 작동한 범위와 테스트 조건을 명확히 적습니다.  
사용하지 않은 기술이나 검증하지 않은 성능을 사실처럼 표시하지 않습니다.

### 6. 대회가 끝나도 정리합니다

제출 이후에도 실행 방법, 주요 기능, 테스트 결과,  
미완성 항목과 다음 프로젝트에서 개선할 점을 남깁니다.

세부 원칙은 [`docs/TEAM_RULES.md`](../docs/TEAM_RULES.md)를 따릅니다.

| Year | Project | Category | Status | Result |
|---|---|---|---|---|
| 2026 | First Team Project | Competition / Project | `Exploring` | - |

각 프로젝트 저장소에는 다음 내용을 기본적으로 남깁니다.

- 문제 정의와 프로젝트 목표
- 핵심 기능과 제외 범위
- 설치 및 실행 방법
- 팀원별 작업 기록
- 프로젝트 구조
- 테스트 결과
- 주요 화면 또는 시연 자료
- 결과와 한계
- 발표 자료와 회고

### Repository Naming

```text
연도-프로젝트명
```

예시:

```text
2026-vision-reliability
2026-ai-learning-assistant
2027-smart-campus
```

공모전 이름보다 프로젝트의 실제 문제와 기능을 중심으로 이름을 정합니다.  
주제와 범위가 확정되기 전에는 빈 프로젝트 저장소를 먼저 만들지 않습니다.

새 프로젝트 시작 전에는  
[`docs/PROJECT_START_CHECKLIST.md`](../docs/PROJECT_START_CHECKLIST.md)를 확인합니다.

## 2026 Goals

첫해에는 많은 프로젝트보다 **첫 번째 완전한 사이클**을 만드는 데 집중합니다.

- [ ] 교수님 자문을 받아 첫 프로젝트 방향 결정
- [ ] 실제 수행할 공모전 또는 프로젝트 하나 선정
- [ ] 팀원별로 직접 작성한 코드 또는 문서 산출물 남기기
- [ ] 최소 기능이 작동하는 프로토타입 완성
- [ ] GitHub Issue를 활용해 작업과 진행 상황 관리
- [ ] 통합 테스트와 시연 수행
- [ ] 공모전 또는 교내 발표 한 차례 이상 참여
- [ ] 프로젝트 종료 후 역할·결과·실패 원인 정리
- [ ] 두 번째 프로젝트에 적용할 작업 방식 만들기

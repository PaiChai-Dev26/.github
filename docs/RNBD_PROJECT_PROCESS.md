# PaiChai Dev 26 R&BD 프로젝트 업무 프로세스

대상: 컴퓨터공학과 1학년 프로젝트팀

이 문서는 문제를 발견한 뒤 제품을 기획하고, 개발하고, 검증하고, 공모전·박람회에서 설명하기까지의
전체 흐름을 안내한다. 기업의 공식 규정이나 투비유니콘의 내부 프로세스가 아니라, PM의 R&BD·특허·
행사·개발 경험을 학생 프로젝트에 맞게 단순화한 교육용 기준이다.

## 1. R&BD란

R&BD는 기술을 만드는 연구개발(R&D)에서 끝나지 않고, 사용자가 실제로 쓸 수 있는 제품과 사업으로
연결하는 과정이다.

```text
문제 조사
  ↓
제품 가설
  ↓
기술 검증
  ↓
사용자 검증
  ↓
시제품
  ↓
사업성·지식재산 검토
  ↓
전시·발표·파일럿
  ↓
개선 또는 중단
```

코드가 동작하는 것만으로 프로젝트가 성공한 것은 아니다. 문제, 사용자, 운영자, 기술, 비용, 위험을
연결해 설명할 수 있어야 한다.

## 2. 전체 단계와 의사결정 게이트

| 단계 | 핵심 질문 | 산출물 | 다음 단계 조건 |
|---|---|---|---|
| Explore | 실제 문제가 있는가? | 조사, 인터뷰 기록 | 반복되는 불편과 담당자 확인 |
| Define | 어떤 문제 하나를 풀 것인가? | 문제 정의, 범위 | 핵심 문제·제외 범위 합의 |
| Plan | 무엇을 언제 누가 만들 것인가? | PRD, 기술계획, 일정 | 완료 기준과 담당자 확정 |
| Spike | 핵심 기술이 가능한가? | 작은 실험, 실패 기록 | 대체 방법 포함 기술 가능성 확인 |
| Build | 전체 흐름이 연결되는가? | 코드, 테스트, 시제품 | 핵심 시나리오 동작 |
| Validate | 사용자에게 실제 가치가 있는가? | 지표, 사용성 결과 | 목표 지표 또는 학습 확보 |
| Protect | 공개 전 권리·보안 검토가 됐는가? | IP 검토표, 공개 범위 | 공개 가능 정보 합의 |
| Present | 짧고 재현 가능하게 설명되는가? | 발표, 영상, 전시 운영표 | 반복 시연과 Q&A 준비 |
| Review | 무엇을 유지·변경·중단할 것인가? | 회고, 다음 결정 | 증거 기반 다음 계획 |

각 단계의 조건을 만족하지 못하면 기능을 늘리지 않는다. 실패한 실험도 결과이며 `docs/evidence/`에
남긴다.

## 3. 문제 조사 프로세스

### 3.1 데스크 리서치

확인할 내용:

- 현재 사용자가 문제를 해결하는 방법
- 유사 서비스·제품
- 운영기관과 담당자
- 관련 법·개인정보·안전 고려사항
- 기존 특허·논문·공개 기술
- 예상 구매자와 예산 출처

검색 결과 링크만 모으지 않는다. 각 자료에서 우리 결정에 영향을 주는 문장과 한계를 함께 적는다.

### 3.2 인터뷰

사용자 의견을 원하는 답으로 유도하지 않는다.

좋은 질문:

- 최근 실제로 어떻게 처리했나요?
- 가장 오래 걸린 단계는 무엇인가요?
- 현재 방식에서 실수가 생기는 지점은 어디인가요?
- 이 기능이 없어도 해결할 수 있나요?
- 도입을 반대할 이유는 무엇인가요?

피해야 할 질문:

- AI로 자동 추천하면 편하시겠죠?
- 스마트 보관함이 있으면 사용하시겠죠?

인터뷰 기록에는 날짜, 대상 역할, 핵심 답변, 확인된 가설, 기각된 가설, 다음 결정을 남긴다. 실명과
연락처는 필요하지 않으면 기록하지 않는다.

### 3.3 문제 정의

```text
[사용자]는 [상황]에서 [현재 어려움]을 겪는다.
그 결과 [시간·비용·위험]이 발생한다.
현재 대안은 [한계]가 있다.
```

FindProof 예시:

> 교내 분실물 담당자는 여러 장소에 분산된 습득물과 신고를 수동으로 비교하고 소유자를 확인해야 한다.
> 학생은 여러 채널을 반복 확인하며, 습득자는 물건을 직접 보관하거나 분실자와 연락하는 부담이 있다.

## 4. PRD 작성 프로세스

PRD는 만들고 싶은 기능 목록이 아니라, 팀이 같은 제품을 만들도록 의사결정을 고정하는 문서다.

### 4.1 필수 목차

1. 한 문장 제품 정의
2. 문제와 근거
3. 사용자와 구매자
4. 핵심 사용자 흐름
5. P0/P1/P2 기능
6. 하지 않을 것
7. 데이터와 개인정보
8. 성공 지표
9. 위험과 대응
10. 완료 기준
11. 미확정 질문
12. 변경 기록

### 4.2 기능 요구사항

기능은 사용자가 얻는 결과로 작성한다.

나쁜 예:

```text
AI 기능 구현
관리자 페이지 개발
```

좋은 예:

```text
분실자는 종류·시간·장소·특징을 입력하고 Top-3 후보와 근거를 확인한다.
관리자는 소유 검증 요청을 승인·반려·추가확인하고 사유를 남긴다.
```

### 4.3 완료 조건

```text
Given: 어떤 전제에서
When: 사용자가 무엇을 하면
Then: 시스템이 어떤 결과를 내야 하는가
```

예:

```text
Given 승인된 반환 요청이 있고
When 사용자가 유효한 QR을 처음 사용하면
Then 지정 보관함이 열리고 감사 로그가 남는다.
```

## 5. 기술계획서 작성 프로세스

기술계획서는 기술 이름을 나열하는 문서가 아니다. 제품 요구사항을 어떤 구조와 검증 방법으로 구현할지
설명한다.

### 5.1 필수 내용

- 시스템 구조도
- 기술 선택과 선택 이유
- 모듈 책임
- 데이터 객체와 상태 전이
- API·장치 계약
- 인증·개인정보·감사 로그
- 테스트 전략
- 개발환경과 CI
- 장애·실패 시 대체 경로
- 기술 전환 조건

### 5.2 기술 선택 표

| 항목 | 선택 | 이유 | 위험 | 전환 조건 |
|---|---|---|---|---|
| API | FastAPI | Python 통합·OpenAPI | 구조가 라우터에 몰림 | 도메인 모듈 분리 |
| DB | SQLite | 로컬 시작 | 동시 사용자 제약 | 파일럿 전 PostgreSQL |
| 장치 | MockLocker | 비용 없이 흐름 검증 | 실제 전기·센서 미검증 | 지원금 후 ESP32 |

“유명해서”, “AI라서”, “최신 기술이라서”는 선택 이유가 아니다.

## 6. 개발 업무 프로세스

### 6.1 Issue

모든 개발은 Issue로 시작한다.

```markdown
## 문제

## 사용자 결과

## 할 일
- [ ]

## 완료 조건
- [ ] 테스트
- [ ] 직접 확인
- [ ] 문서·증거

## 제외 범위

## 난이도
L1 / L2 / L3 / Spike
```

### 6.2 작은 수직 기능

DB만 만들거나 화면만 여러 개 만드는 방식보다 사용자 행동 하나를 끝까지 연결한다.

```text
화면 입력 → API 검증 → 도메인 규칙 → DB → 결과 화면 → 테스트
```

### 6.3 PR

PR에는 다음을 포함한다.

- 왜 변경했는가
- 무엇이 달라졌는가
- 어떻게 테스트했는가
- 화면·API·장치 증거
- 남은 위험
- 관련 Issue

### 6.4 완료 정의

기능은 다음을 모두 만족해야 완료다.

- 완료 조건 충족
- `make check` 통과
- 비밀정보·개인정보 없음
- 다른 팀원이 읽음
- 실행 방법 또는 API 변경 문서화
- 실패 경로 테스트
- 시연 가능한 상태

## 7. Evidence 기반 개발

발표 직전에 증거를 만들지 않는다. 개발할 때마다 남긴다.

`docs/evidence/` 권장 구조:

```text
docs/evidence/
├── interviews/
├── matching/
├── usability/
├── locker/
├── security/
└── demos/
```

기록 항목:

- 실험 목적
- 환경과 데이터
- 실행 방법
- 기대 결과
- 실제 결과
- 실패 원인
- 다음 결정
- 작성자와 날짜

숫자에는 측정 조건을 붙인다. “정확도 90%” 대신 “통제 데이터 50쌍에서 Top-3 포함률 90%”라고 쓴다.

## 8. R&BD 의사결정 기록

중요한 범위·기술·사업 결정은 `docs/decisions/`에 남긴다.

```markdown
# 결정 제목

## Decision

## Evidence

## Alternatives

## Impact

## Owner / Date
```

예:

- 하드웨어 지원금 전 MockLocker 우선
- 이미지 AI는 기준선 개선 후 채택
- 캠퍼스 전체가 아닌 생활관 우선 실증

## 9. 지식재산 검토 프로세스

이 항목은 법률 자문이 아니다. 출원 가능성·권리관계가 중요하면 지도교수, 산학협력단 또는 변리사에게
확인한다.

### 9.1 아이디어 기록

- 문제와 해결 원리
- 기존 방식과 차이
- 핵심 구성과 동작 순서
- 최초 제안자와 기여자
- 작성 날짜
- 관련 도면·실험

Git Commit은 개발 이력의 보조 증거지만, 발명자·권리자를 자동으로 결정하지 않는다.

### 9.2 선행기술 조사

KIPRIS에서 특허·실용신안·디자인·상표를 검색한다.

검색 과정:

1. 핵심 문제 키워드
2. 해결 수단 키워드
3. 유사어·영문 표현
4. 관련 IPC/CPC 확인
5. 비슷한 문헌의 청구항·도면 확인
6. 우리 기술과 공통점·차이 기록

검색 결과가 없다고 특허 가능성이 확정되는 것은 아니다. KIPRIS는 국내외 지식재산정보를 검색·열람할
수 있는 공식 서비스이며, 학생팀은 출원 여부 결정 전 기초 선행기술조사에 활용한다.

### 9.3 공개 전 체크

다음 공개 전에 IP 검토 여부를 확인한다.

- GitHub 공개 저장소
- 공모전 제출
- 발표자료·시연 영상
- 박람회 전시
- 논문·포스터·SNS

전시·박람회·발표는 기술 공개가 될 수 있으므로, 출원을 고려하는 핵심 기술이 있다면 먼저 학교
산학협력단 또는 전문가와 공개 범위를 검토한다. 이미 공개했다면 날짜·장소·자료를 기록하고 즉시
전문가에게 알린다.

### 9.4 권리별 구분

- 특허·실용신안: 기술적 아이디어와 구조
- 디자인: 제품 외관
- 상표: FindProof·FindBox 같은 이름과 표지
- 저작권: 소스코드, 문서, 이미지
- 영업비밀: 공개하지 않고 관리할 기술·운영 정보

이름을 정했다고 상표권이 생기는 것은 아니다. 사용 전 유사 상표를 검색하고, 외부 이미지·모델·코드의
라이선스를 기록한다.

## 10. 사업계획서 작성 프로세스

### 10.1 흐름

```text
문제 → 고객 → 해결방법 → 차별성 → 검증 → 시장 진입 → 수익 → 비용 → 팀 → 일정 → 위험
```

### 10.2 반드시 구분할 것

- 사용자: 제품을 직접 쓰는 사람
- 구매자: 예산을 승인하고 비용을 지불하는 기관
- 수혜자: 결과의 혜택을 받는 사람
- 운영자: 매일 시스템을 관리하는 사람

FindProof에서는 학생이 사용자, 생활관·학생지원 부서가 구매자이자 운영자다.

### 10.3 숫자 작성

근거 없는 큰 시장 규모보다 첫 고객 확보 경로를 구체적으로 쓴다.

- 첫 실증 장소
- 담당자 인터뷰 여부
- 월 분실물 건수
- 현재 처리시간
- 도입 전후 목표
- 시제품 비용
- 지원금과 사비 구분

가정은 “확정”이 아니라 “가설”로 표시한다.

## 11. 공모전 신청서 프로세스

### 11.1 문항 분해

신청서 문항마다 다음을 정한다.

| 항목 | 내용 |
|---|---|
| 질문 의도 | 심사위원이 확인하려는 것 |
| 핵심 답변 | 한 문장 결론 |
| 근거 | 인터뷰·테스트·자료 |
| 담당자 | 초안 작성자 |
| 검토자 | 사실·문체 확인자 |
| 상태 | 초안/검토/완료 |

### 11.2 작성 순서

1. 분량 제한과 제출 양식 확인
2. 문항별 한 문장 결론 작성
3. 근거와 수치 배치
4. 팀원별 초안
5. PM이 용어·수치 통일
6. 실제 구현과 개발 예정 구분
7. 최종 PDF/HWP 렌더링 확인
8. 제출 파일·동의서·서명 확인

다른 문서에서 같은 수치가 다르게 나오지 않도록 기준표를 하나만 운영한다.

## 12. 행사·박람회 기획 프로세스

### 12.1 전시 목표

전시 목표를 하나 고른다.

- 심사 통과
- 사용자 피드백
- 실증기관 발굴
- 지도·투자·협력 요청
- 기술 검증

모든 관람객에게 모든 내용을 설명하려 하지 않는다.

### 12.2 부스 메시지

관람객은 5초 안에 다음을 이해해야 한다.

1. 누구의 어떤 문제인가
2. 제품이 무엇을 하는가
3. 무엇이 실제로 동작하는가

FindProof 한 문장:

> AI 후보 추천과 기관 검증을 통해 습득자와 분실자가 직접 연락하지 않고 안전하게 반환하는 대학용
> 분실물 운영 시스템

### 12.3 시연 구성

```text
30초: 문제와 제품
2분: 습득 등록 → 신고 → Top-3
2분: 소유 검증 → 승인 → QR 반환
1분: 지표·실패 대응·확장
```

실제 장치가 실패할 수 있으므로 준비한다.

- 라이브 시연
- 로컬 서버
- 녹화 영상
- 화면 캡처
- MockLocker
- 수동 진행 대본

### 12.4 운영표

| 역할 | 책임 |
|---|---|
| 발표 | 5분 설명과 Q&A |
| 시연 | 데이터 초기화와 전체 흐름 |
| 장치 | 전원·네트워크·잠금 상태 |
| 기록 | 질문·관심기관·피드백 |

3인 팀에서는 한 명이 두 역할을 맡되 교대 시간을 정한다.

### 12.5 전날 체크리스트

- 노트북·충전기·멀티탭
- 오프라인 실행 가능 여부
- 테스트 계정과 가상 데이터
- QR 인쇄본
- 시연 영상 로컬 복사
- 보관함 수동 개방 방법
- 부품·공구·예비 배선
- 발표자료 PDF
- 개인정보 없는 화면
- 팀 연락망과 행사 일정

## 16. 변경관리

새 기능 아이디어가 나오면 바로 개발하지 않는다.

```text
요청 내용:
사용자 가치:
근거:
일정 영향:
기술 위험:
P0/P1/P2:
결정:
```

P0 기능을 추가하려면 기존 P0 하나를 줄일 수 있는지 함께 검토한다.

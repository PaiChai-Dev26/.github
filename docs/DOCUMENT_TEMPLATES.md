# 복사해서 바로 쓰는 프로젝트 문서 템플릿

문서를 잘 쓰는 사람은 빈 화면을 오래 보지 않는다. 필요한 양식을 복사하고, 모르는 칸은 지어내지 않고
`미확인`이라고 적는다.

## 어떤 문서를 써야 하지?

| 상황 | 사용할 양식 |
| --- | --- |
| 사용자 말을 들었다 | 인터뷰 기록 |
| 팀에서 결정을 내렸다 | 회의록 또는 결정 기록 |
| 만들 기능을 합의한다 | 미니 PRD |
| 구현 방법을 정한다 | 기술계획 또는 기술결정 |
| 불확실한 기술을 시험한다 | 실험 기록 |
| 한 주를 정리한다 | 주간 보고 |
| 프로젝트가 끝났다 | 회고 |

## 1. 사용자 인터뷰 기록

```markdown
# 인터뷰 기록

- 날짜:
- 인터뷰어:
- 대상 역할: 사용자 / 운영자 / 구매·결정자
- 장소·방식:
- 개인정보 수집 여부: 없음 / 있음(이유와 보관기간)

## 확인하려던 가설

## 실제로 겪은 최근 사례

## 현재 해결 방법

## 불편·비용·위험

## 기억할 발언
> 짧은 범위만 익명으로 기록

## 우리가 잘못 예상했던 점

## 다음에 검증할 질문
```

“필요하세요?”보다 “마지막으로 이런 일을 겪었을 때 무엇을 했나요?”를 묻는다.

## 2. 30분 회의록

```markdown
# 회의 제목

- 날짜·시간:
- 참석자:
- 오늘 끝낼 결정:

## 5분 — 현재 사실

## 10분 — 선택지
1.
2.

## 10분 — 결정과 근거

## 5분 — 다음 행동
| 할 일 | 담당 | 완료일 | 완료 조건 |
| --- | --- | --- | --- |

## 보류한 내용
```

회의록은 대화를 모두 받아쓰는 문서가 아니라 결정과 다음 행동을 남기는 문서다.

## 3. 미니 PRD

```markdown
# 기능 이름

## 한 문장 문제
[사용자]는 [상황]에서 [문제]를 겪는다.

## 목표

## 제외 범위

## 사용자 흐름
1.
2.
3.

## 요구사항
- [ ]

## 완료 조건
- Given:
- When:
- Then:

## 성공 지표

## 위험·미확인 사항
```

## 4. 기술계획서

```markdown
# 기술계획: 기능 이름

## 입력 → 처리 → 출력

## 바뀌는 파일·컴포넌트

## 데이터 구조

## API 또는 장치 인터페이스

## 정상 상태와 실패 상태

## 보안·개인정보

## 테스트 계획

## 배포·되돌리기

## 하지 않을 것
```

## 5. 기술 의사결정 기록(ADR)

```markdown
# 결정 제목

- 날짜:
- 상태: 제안 / 결정 / 폐기 / 대체
- 참여자:

## 상황

## 비교한 선택지
| 선택지 | 장점 | 단점 | 근거 |
| --- | --- | --- | --- |

## 결정

## 결과와 감수한 단점

## 다시 검토할 조건
```

결정이 바뀌어도 이전 기록을 몰래 고치지 말고 새 ADR에서 대체 이유를 남긴다.

## 6. 기술 실험(Spike) 기록

```markdown
# 실험 제목

- 담당:
- 시간 제한:
- 질문:
- 성공 기준:

## 최소 실험 방법

## 데이터·환경

## 결과

## 실패 사례

## 결론
채택 / 보류 / 폐기

## 다음 행동
```

실험의 목적은 성공 영상을 만드는 것이 아니라 불확실성을 줄이는 것이다.

## 7. 주간 업무보고

```markdown
# 주간 기록 — YYYY-MM-DD

## 이번 주 완료
- 결과 링크와 함께 작성

## 확인한 증거

## 막힌 점

## 다음 주 가장 중요한 한 가지

## 도움이 필요한 것

## 역할·일정 조정 필요 여부
```

“열심히 했음” 대신 PR·화면·인터뷰·테스트 등 확인 가능한 결과를 연결한다.

## 8. 시연 대본

```markdown
# 시연 대본

## 20초 문제 소개

## 90초 핵심 흐름
1.
2.
3.

## 보여줄 결과 숫자

## 실패 시 대체 화면·영상

## 예상 질문과 담당자

## 시연 전 확인
- [ ] 네트워크
- [ ] 테스트 계정·데이터
- [ ] 화면 확대와 알림 끄기
- [ ] 충전기·케이블
- [ ] 오프라인 자료
```

## 9. 프로젝트 회고

```markdown
# 프로젝트 회고

## 처음 목표와 실제 결과

## 계속할 것(Keep)

## 문제가 된 것(Problem)

## 다음에 시도할 것(Try)

## 개인별 실제 기여

## 실패와 원인

## 다음 프로젝트에 넘길 자산
- 코드:
- 문서:
- 데이터:
- 연락·운영 지식:

## 한 문장 결론
```

## 문서를 닫기 전 세 질문

1. 이 문서만 읽은 다른 팀원이 다음 행동을 알 수 있는가?
2. 사실·추정·희망이 구분되어 있는가?
3. 담당자·기한·완료 조건 중 빠진 것이 없는가?

세 질문에 답했다면 문서는 길지 않아도 충분하다.
